## 1. 项目背景

### 1.1 业务背景

企业仓储管理通常涉及商品资料维护、入库、出库、调拨、盘点、库存冻结、库存预警、审批和审计等流程。传统仓管系统能够处理基础单据和库存查询，但在异常发现、自然语言查询、跨模块分析、风险解释和智能决策辅助方面能力有限。

本项目计划建设一个基于 FastAPI、MySQL、Redis、LangGraph 和 Vue3 的智能 ERP 仓管系统，在保证库存数据准确、流程可控、操作可追溯的前提下，引入多智能体能力，帮助仓管员、仓库主管和管理人员更高效地完成日常仓储业务。

系统定位为真实企业可用的仓管平台，而不是演示型聊天机器人。库存变更、单据状态流转、审批和审计必须由确定性后端业务逻辑控制；智能体主要负责查询、分析、预警、解释和生成业务草稿。

### 1.2 问题陈述

当前仓库管理场景中常见问题包括：

- 库存数据分散，无法快速查询 SKU 在不同仓库、库区、库位和批次下的真实库存。
- 出入库流程依赖人工判断，容易出现重复提交、漏记、错扣和超卖问题。
- 库存异常发现滞后，例如低库存、临期、呆滞、负库存、盘点差异等问题需要人工排查。
- 库存变更缺少完整流水和审计链路，后续追责、复盘和财务对账困难。
- 传统 ERP 操作页面学习成本较高，新员工需要较长时间熟悉业务菜单和查询方式。
- 管理者希望用自然语言快速了解库存风险、发货风险和待处理事项，但普通系统难以支持。
- AI 如果直接操作库存又存在安全风险，必须建立受控工具调用和人工确认机制。

### 1.3 项目目标

项目核心目标如下：

- 建立真实可用的仓管业务闭环，覆盖基础资料、入库、出库、调拨、盘点、库存调整和预警。
- 使用 MySQL 作为最终事实数据源，保存单据、库存快照、库存流水、审批和审计数据。
- 使用 Redis 支撑热点缓存、分布式锁、幂等控制、异步任务状态和 AI 会话状态。
- 建立库存快照与库存流水双账模型，保证库存既能快速查询，又能完整追溯。
- 通过 FastAPI 实现清晰的接口边界、业务服务层和权限控制。
- 通过 LangGraph 构建多智能体协作层，实现自然语言查库存、查单据、异常分析、单据草稿生成和报表辅助。
- 通过 Vue3 提供传统 ERP 工作台和 AI 智能工作台，提升业务人员操作效率。
- 建立权限、审批、审计和风险控制机制，确保系统具备企业级可控性。

## 2. 用户分析

### 2.1 目标用户

| 用户角色 | 描述 | 核心需求 |
|----------|------|----------|
| 系统管理员 | 负责系统配置、用户、角色、权限和基础参数维护 | 管理账号权限、配置系统字典、查看系统运行状态 |
| 仓库主管 | 负责仓库整体运营、审批、异常处理和库存风险控制 | 查看库存全局情况、处理审批、分析异常、生成经营报表 |
| 仓管员 | 负责日常入库、出库、上架、拣货、复核、盘点等操作 | 快速处理单据、准确录入库存、减少误操作 |
| 采购协同员 | 关注采购到货、入库进度和缺货补货 | 查看待入库、到货差异、低库存和补货建议 |
| 销售协同员 | 关注订单发货能力和库存可用性 | 查询可用库存、发货风险、锁库状态和出库进度 |
| 财务查看员 | 关注库存流水、库存调整和后续成本核算依据 | 查看库存变更记录、导出对账数据、追溯业务单据 |
| 审计员 | 负责追踪关键操作、权限变化和异常库存处理 | 查看操作日志、审批记录、智能体调用记录和库存流水 |

### 2.2 用户画像

典型用户包括一线仓管员、仓库主管和管理层。

一线仓管员更关注操作效率和准确性，常用功能包括扫码查询、入库确认、出库拣货、复核、库位调整和盘点录入。该类用户希望页面直接、流程清晰、错误提示明确，尽量减少复杂配置。

仓库主管更关注库存状态、异常处理和流程管控，常用功能包括库存看板、审批中心、预警中心、盘点差异处理、呆滞料分析和报表导出。该类用户需要系统提供风险解释和处理建议。

管理层更关注整体库存健康度和经营风险，例如库存周转、缺货风险、临期风险和库存占用情况。该类用户更适合通过 AI 智能工作台使用自然语言查询和获取摘要报告。

### 3.2 详细功能描述

#### 3.2.1 用户与权限模块

**功能描述**：

提供登录认证、用户管理、角色管理、菜单权限、按钮权限、API 权限和仓库数据范围控制能力。

**用户故事**：

- 作为系统管理员，我希望能够给不同岗位分配不同权限，以便控制用户只能访问和操作授权范围内的数据。
- 作为仓库主管，我希望仓管员只能操作自己负责的仓库，以便降低误操作和越权操作风险。

**验收标准**：

- [ ] 支持用户登录、退出和登录状态校验。
- [ ] 支持角色创建、编辑、禁用和授权。
- [ ] 支持按仓库配置数据访问范围。
- [ ] 未授权用户访问接口时返回明确错误。
- [ ] 高风险接口必须校验用户角色和操作权限。

**输入**：账号、密码、角色、权限配置、仓库数据范围。

**输出**：登录令牌、用户信息、角色权限、授权结果。

**业务规则**：

- 用户必须登录后才能访问业务接口。
- 用户只能查看和操作授权仓库范围内的数据。
- 权限变更必须写入审计日志。

#### 3.2.2 基础资料模块

**功能描述**：

维护商品、SKU、仓库、库区、库位、供应商、客户、批次规则和库存预警规则等基础资料。

**用户故事**：

- 作为仓库主管，我希望维护 SKU 和库位信息，以便后续库存业务能够准确关联商品和存储位置。
- 作为仓管员，我希望通过条码快速识别 SKU，以便减少手工录入错误。

**验收标准**：

- [ ] 支持商品和 SKU 的新增、编辑、禁用、查询。
- [ ] 支持仓库、库区、库位三级结构维护。
- [ ] 支持 SKU 条码、单位、规格、保质期、最小库存和最大库存维护。
- [ ] 基础资料被业务单据使用后不得物理删除，只能禁用。

**输入**：商品资料、SKU 资料、仓库资料、库区库位资料、供应商和客户信息。

**输出**：基础资料列表、详情、启停用状态。

**业务规则**：

- SKU 编码、仓库编码、库位编码必须唯一。
- 被库存或单据引用的数据不能物理删除。
- 库位必须归属到具体库区，库区必须归属到具体仓库。

#### 3.2.3 库存核心模块

**功能描述**：

提供库存快照、库存流水、库存查询、库存冻结、库存释放、库存扣减和库存调整能力。

**用户故事**：

- 作为仓管员，我希望快速查看某个 SKU 在不同库位和批次下的库存，以便安排出入库操作。
- 作为财务查看员，我希望追溯每一次库存变化，以便核对库存差异来源。

**验收标准**：

- [ ] 支持按 SKU、仓库、库位、批次查询库存。
- [ ] 支持现存量、可用量、锁定量、冻结量和在途量展示。
- [ ] 每次库存变化必须生成库存流水。
- [ ] 库存变更必须在 MySQL 事务中完成。
- [ ] 并发出库不能导致可用库存小于 0。

**输入**：SKU、仓库、库位、批次、库存变更数量、业务单据号。

**输出**：库存快照、库存流水、库存变更结果。

**业务规则**：

- MySQL 是库存最终事实来源，Redis 不能作为最终库存依据。
- 库存快照用于快速查询，库存流水用于审计追溯。
- 关键库存写操作必须使用 Redis 锁和 MySQL 行级锁。

#### 3.2.4 入库管理模块

**功能描述**：

支持入库单创建、审核、收货、上架、确认入库和库存流水生成。

**用户故事**：

- 作为仓管员，我希望根据到货情况创建入库单并确认入库，以便系统库存及时增加。
- 作为仓库主管，我希望审核异常入库单，以便防止错误数据进入库存。

**验收标准**：

- [ ] 支持创建入库单草稿。
- [ ] 支持入库单提交审核。
- [ ] 支持入库单确认后增加库存。
- [ ] 支持按批次、生产日期、有效期入库。
- [ ] 入库完成后必须生成库存流水和审计日志。

**输入**：入库单头、入库明细、SKU、数量、批次、库位、供应商。

**输出**：入库单状态、库存增加结果、库存流水。

**业务规则**：

- 未审核的入库单不能确认入库。
- 入库数量必须大于 0。
- 已完成入库单不能重复确认。

#### 3.2.5 出库管理模块

**功能描述**：

支持出库单创建、审核、库存锁定、拣货、复核、确认出库和库存扣减。

**用户故事**：

- 作为仓管员，我希望系统在出库前锁定库存，以便避免多人同时操作造成超卖。
- 作为销售协同员，我希望查看订单是否具备发货能力，以便及时处理缺货风险。

**验收标准**：

- [ ] 支持创建出库单草稿。
- [ ] 支持审核后锁定库存。
- [ ] 支持拣货和复核状态流转。
- [ ] 确认出库后必须扣减库存并生成库存流水。
- [ ] 重复提交同一出库确认请求不能重复扣减库存。

**输入**：出库单头、出库明细、SKU、数量、仓库、库位、客户。

**输出**：出库单状态、锁库结果、库存扣减结果、库存流水。

**业务规则**：

- 可用库存不足时不能完成锁库。
- 已完成出库单不能再次确认。
- 出库扣减必须使用幂等 key、Redis 锁和 MySQL 事务。

#### 3.2.6 调拨管理模块

**功能描述**：

支持同仓库不同库位之间、不同仓库之间的库存调拨流程。

**用户故事**：

- 作为仓库主管，我希望根据库存分布创建调拨单，以便平衡不同仓库或库位的库存。

**验收标准**：

- [ ] 支持创建调拨单。
- [ ] 支持源库位库存锁定或冻结。
- [ ] 支持形成在途库存。
- [ ] 支持目标库位确认入库。
- [ ] 调拨全过程必须生成库存流水。

**输入**：源仓库、源库位、目标仓库、目标库位、SKU、批次、数量。

**输出**：调拨单状态、源库存变化、在途库存、目标库存变化。

**业务规则**：

- 源库位可用库存不足时不能发起调拨出库。
- 调拨完成前目标库位不能提前增加可用库存。
- 调拨取消时必须释放已锁定库存。

#### 3.2.7 盘点管理模块

**功能描述**：

支持创建盘点任务、冻结盘点范围、录入实盘数量、生成差异、审核差异和盘盈盘亏过账。

**用户故事**：

- 作为仓管员，我希望录入实盘数量并自动生成差异，以便减少人工计算错误。
- 作为仓库主管，我希望审批盘点差异后再调整库存，以便保证库存调整可控。

**验收标准**：

- [ ] 支持按仓库、库区、库位、SKU 范围创建盘点任务。
- [ ] 盘点期间相关库存可以被冻结。
- [ ] 支持录入实盘数量并自动计算差异。
- [ ] 盘点差异必须审批后才能过账。
- [ ] 盘点过账必须生成库存流水和审计日志。

**输入**：盘点范围、账面数量、实盘数量、差异原因。

**输出**：盘点任务、差异明细、审批结果、库存调整流水。

**业务规则**：

- 盘点冻结范围内不允许进行普通出库和库存调整。
- 未审批差异不能过账。
- 盘点过账后不能直接删除盘点记录。

#### 3.2.8 预警与异常分析模块

**功能描述**：

自动发现低库存、临期、呆滞、负库存、超卖风险、库存不一致和长时间未处理单据。

**用户故事**：

- 作为仓库主管，我希望系统自动提醒库存异常，以便及时安排补货、调拨或盘点。

**验收标准**：

- [ ] 支持低库存预警。
- [ ] 支持临期库存预警。
- [ ] 支持呆滞库存识别。
- [ ] 支持出库缺货风险识别。
- [ ] 支持 AI 解释异常原因并给出处理建议。

**输入**：库存快照、库存流水、出入库单据、预警规则。

**输出**：预警列表、异常说明、处理建议。

**业务规则**：

- 预警规则应支持按 SKU、分类、仓库配置。
- AI 建议不能自动执行高风险库存动作。
- 已处理预警需要记录处理人、处理时间和处理结果。

#### 3.2.9 AI 智能工作台与多智能体模块

**功能描述**：

通过 LangGraph 构建多智能体协作能力，支持自然语言查询、异常分析、单据草稿生成、报表摘要和操作建议。

**用户故事**：

- 作为仓库主管，我希望直接询问“今天哪些 SKU 影响发货”，以便快速识别风险。
- 作为仓管员，我希望 AI 根据到货信息生成入库单草稿，以便减少重复录入。

**验收标准**：

- [ ] 支持自然语言查询库存和单据。
- [ ] 支持 AI 生成入库单、出库单、调拨单草稿。
- [ ] 支持 AI 对异常库存进行原因解释。
- [ ] 智能体工具调用必须经过权限校验和审计记录。
- [ ] 高风险动作必须人工确认或审批。

**输入**：用户自然语言、业务上下文、当前页面上下文、用户权限。

**输出**：自然语言回答、工具调用结果、草稿单据、预警解释、建议动作。

**业务规则**：

- 智能体不能直接连接 MySQL 修改业务数据。
- 智能体只能通过 Tool Gateway 调用后端 Service。
- 高风险建议只能生成草稿或审批请求，不能自动过账。

#### 3.2.10 审批与审计模块

**功能描述**：

支持库存调整、盘点差异、报损、批量修改和高风险 AI 建议的审批；同时记录关键业务操作和系统调用日志。

**用户故事**：

- 作为审计员，我希望查看某次库存调整的操作人、审批人和变更前后数据，以便追溯责任。

**验收标准**：

- [ ] 支持高风险操作提交审批。
- [ ] 支持审批通过、驳回和备注。
- [ ] 支持审计日志查询。
- [ ] 支持记录智能体工具调用日志。
- [ ] 审计日志不能被普通用户删除或篡改。

**输入**：审批对象、审批意见、业务操作、变更前后数据。

**输出**：审批记录、审计日志、操作追踪结果。

**业务规则**：

- 库存调整、盘点过账、批量报损必须审批。
- 审批人与提交人原则上不能为同一人。
- 审计日志必须包含操作人、时间、模块、业务单号和关键变更内容。

## 4. 非功能需求

### 4.1 性能需求

| 指标 | 要求 |
|------|------|
| 普通查询响应时间 | 95% 请求在 1 秒内返回 |
| 库存查询响应时间 | 命中 Redis 缓存时 300ms 内返回，未命中时 1 秒内返回 |
| 单据提交响应时间 | 普通单据 2 秒内返回处理结果 |
| AI 查询响应时间 | 简单查询 5 秒内返回，复杂分析支持异步任务 |
| 并发用户数 | 第一阶段支持 50-200 名企业内部用户同时在线 |
| 数据量 | 第一阶段支持 10 万级 SKU、百万级库存流水，后续可扩展 |

### 4.2 安全需求

- [ ] 支持登录认证和 Token 鉴权。
- [ ] 支持 RBAC 角色权限控制。
- [ ] 支持仓库级数据范围控制。
- [ ] 支持关键接口权限校验。
- [ ] 支持操作审计日志。
- [ ] 支持密码加密存储。
- [ ] 支持敏感配置通过环境变量管理。
- [ ] 支持智能体工具调用权限校验。
- [ ] 高风险 AI 操作必须人工确认或审批。

### 4.3 可用性需求

- 系统界面应适合仓库现场高频操作，常用功能入口清晰。
- 入库、出库、盘点等流程应提供明确状态提示和错误说明。
- 表格页面应支持搜索、筛选、分页、导出和状态标识。
- AI 工作台应能结合当前页面上下文提供业务建议。
- 高风险操作前应显示确认信息和影响范围。

### 4.4 兼容性需求

- 前端支持主流现代浏览器，包括 Chrome、Edge 和 Firefox。
- 后端支持通过 Docker Compose 在企业内网环境部署。
- 数据库采用 MySQL 8，缓存采用 Redis 6 或以上版本。
- API 采用 REST 风格，便于后续对接采购、销售、财务和第三方系统。

### 4.5 可维护性需求

- 后端采用模块化结构，每个业务模块保持清晰边界。
- 核心业务逻辑放在 Service 层，不直接写在 Router 中。
- 数据库变更通过 Alembic 管理。
- 关键业务流程需要单元测试和接口测试覆盖。
- 日志应采用结构化格式，便于排查问题。
- 智能体工具调用需要有可追踪记录，便于调试和审计。

## 5. 数据需求

### 5.1 数据实体

| 实体 | 描述 | 关键属性 |
|------|------|----------|
| 用户 | 系统登录和操作主体 | 用户ID、账号、姓名、状态、角色ID |

| 库区 | 仓库下的区域 | 库区ID、仓库ID、库区编码、名称 |
| 库位 | 具体存储位置 | 库位ID、库区ID、库位编码、状态 |
| 库存快照 | 当前库存余额 | SKU、仓库、库位、批次、现存量、可用量、锁定量、冻结量 |
| 库存流水 | 每次库存变化记录 | 业务类型、业务单号、变动数量、变动前后数量、操作人 |
| 入库单 | 入库业务单据 | 单号、供应商、状态、明细、创建人、审核人 |
| 出库单 | 出库业务单据 | 单号、客户、状态、明细、锁库状态、复核状态 |
| 调拨单 | 仓库或库位间调拨单据 | 源仓库、目标仓库、SKU、数量、状态 |

| 审计日志 | 关键操作追踪记录 | 操作人、模块、动作、业务单号、变更前后数据 |
| 智能体会话 | AI 对话上下文 | 会话ID、用户ID、消息、工具调用记录、状态 |

### 5.2 数据流

核心数据流如下：

```text
基础资料录入
→ 创建业务单据
→ 审核或确认业务动作
→ MySQL 事务处理库存快照
→ 追加库存流水
→ 写入审计日志
→ 删除或刷新 Redis 缓存
→ 前端展示最新业务结果
```

AI 数据流如下：

```text
用户自然语言输入
→ FastAPI 接收请求并校验权限
→ LangGraph Supervisor 判断意图
→ 专业智能体选择受控工具
→ Tool Gateway 校验权限和风险
→ 调用后端 Service 查询或生成草稿
→ 返回分析结果、建议动作或草稿单据
→ 记录智能体调用日志
```

### 5.3 数据存储

| 数据类型 | 存储方式 | 保留策略 |
|----------|----------|----------|
| 用户、角色、权限 | MySQL | 长期保留，禁用不物理删除 |
| 基础资料 | MySQL | 长期保留，被引用后不物理删除 |
| 业务单据 | MySQL | 长期保留，支持状态归档 |
| 库存快照 | MySQL + Redis 缓存 | MySQL 长期保留，Redis 设置过期或主动失效 |
| 库存流水 | MySQL | 长期保留，原则上只追加不修改 |
| 审批记录 | MySQL | 长期保留 |
| 审计日志 | MySQL | 长期保留或按企业合规策略归档 |
| 幂等 Key | Redis | 短期保留，根据业务请求有效期设置 TTL |
| 分布式锁 | Redis | 短期保留，必须设置过期时间 |
| AI 会话上下文 | Redis + MySQL 可选归档 | 短期上下文存 Redis，重要调用记录落 MySQL |
| 异步任务状态 | Redis | 任务完成后保留短期查询窗口 |

## 7. 约束条件

### 7.1 技术约束

- 后端使用 FastAPI。
- 后端采用 MVC/分层架构，建议落地为 Router、Schema、Service、Repository、Model。
- 数据库使用 MySQL，不使用 PostgreSQL。
- 缓存和并发控制使用 Redis。
- 多智能体编排使用 LangGraph。
- 前端使用 Vue3。
- 库存写操作必须通过后端 Service，不允许前端或智能体直接操作数据库。

### 7.2 业务约束

- MySQL 是业务事实来源，Redis 不能作为最终库存依据。
- 库存变化必须有业务单据或审批依据。
- 所有库存变化必须产生库存流水。
- 盘点差异、库存调整、报损等高风险动作必须审批。
- 智能体只能生成建议或草稿，高风险动作必须人工确认。

### 7.3 资源约束

- 第一阶段建议以模块化单体为主，避免过早拆成复杂微服务。
- 第一阶段优先完成 WMS 仓管核心闭环，采购、销售、财务等 ERP 模块以接口预留为主。
- 初期部署可使用 Docker Compose，后续根据企业规模升级为更复杂的部署方案。
- AI 能力应优先覆盖查询、分析和草稿生成，不宜第一版追求全自动库存决策。

## 8. 风险分析

| 风险 | 影响 | 概率 | 应对措施 |
|------|------|------|----------|
| 并发出库导致库存超扣 | 高 | 中 | Redis 分布式锁 + MySQL 事务 + SELECT FOR UPDATE 行级锁 |
| 重复提交导致重复扣减或重复入库 | 高 | 中 | 所有关键写操作增加幂等 key |
| Redis 缓存与 MySQL 数据不一致 | 中 | 中 | MySQL 事务成功后删除缓存，后续查询重新加载 |
| 智能体生成错误业务建议 | 中 | 中 | 智能体只生成建议或草稿，高风险动作必须人工确认 |
| 智能体越权查询或操作 | 高 | 中 | Tool Gateway 统一做用户权限和数据范围校验 |
| 单据状态流转混乱 | 高 | 中 | 建立统一状态机，不允许绕过业务 Service 修改状态 |
| 库存调整缺少追溯 | 高 | 低 | 库存调整必须审批，并写库存流水和审计日志 |
| 大量库存查询导致数据库压力过高 | 中 | 中 | 热点数据使用 Redis 缓存，查询接口分页和索引优化 |
| 第一阶段范围过大导致延期 | 中 | 高 | MVP 聚焦仓管核心，暂缓财务、生产、高级 BI 等功能 |
| 用户不信任 AI 输出 | 中 | 中 | 展示数据来源、工具调用结果和建议依据，保留人工确认流程 |

## 9. 验收标准

### 9.1 功能验收

- [ ] 所有 P0 功能完成，包括用户权限、基础资料、库存核心、入库、出库和审计日志。
- [ ] 至少完成 P1 中的库存预警、审批中心和 AI 自然语言查询能力。
- [ ] 入库确认后能够正确增加库存快照并生成库存流水。
- [ ] 出库确认后能够正确扣减库存快照并生成库存流水。
- [ ] 并发出库测试中不能出现可用库存小于 0。
- [ ] 重复提交同一请求不能重复影响库存。
- [ ] AI 查询库存时必须通过受控工具调用后端 Service。
- [ ] 高风险 AI 建议不能绕过人工确认或审批直接执行。
- [ ] 操作日志、审批日志、库存流水可以按业务单号追溯。
- [ ] 测试通过率达到 90% 以上，核心库存服务测试必须全部通过。

### 9.2 性能验收

- [ ] 普通列表查询 95% 请求在 1 秒内返回。
- [ ] Redis 命中场景下库存查询在 300ms 内返回。
- [ ] 入库、出库确认接口在正常数据量下 2 秒内返回。
- [ ] 系统可支持 50-200 名企业内部用户同时在线。
- [ ] 百万级库存流水下仍可分页查询并按索引条件过滤。

### 9.3 文档验收

- [ ] 需求分析文档包含项目背景、用户分析、功能需求、非功能需求、数据需求、接口需求、约束条件、风险分析和验收标准。
- [ ] 所有 P0 功能具备明确功能描述、用户故事、验收标准、输入、输出和业务规则。
- [ ] 技术约束明确标注 MySQL、Redis、FastAPI、LangGraph 和 Vue3。
- [ ] 明确说明智能体不能直接修改数据库，必须通过受控业务服务执行。
