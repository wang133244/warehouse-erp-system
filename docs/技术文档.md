## 1. 逻辑架构

```text
┌─────────────── 浏览器 ───────────────┐
│ Vue 3 View  → Controller → models/* │
│ Pinia token / pendingDraft          │
│ fetch + Bearer + Idempotency-Key    │
└──────────────────┬──────────────────┘
                   │ HTTP / JSON / CSV
┌──────────────────▼──────────────────┐
│ FastAPI 0.2.0                       │
│ CORS → X-Request-ID → 运行日志 → JWT → RBAC    │
│ Controller → Service → ORM          │
│ inventory_service 唯一写库存        │
│ LangGraph supervisor → 白名单工具   │
└───────┬───────────────┬─────────────┘
        │               │
   MySQL 8 erp_wms   Redis（可选，可丢）
   事实 + 流水 + 幂等   看板缓存 / JWT 黑名单 / 库存锁
```

分层职责：

| 层 | 允许 | 禁止 |
|---|---|---|
| View | 渲染、路由、表单 | 拼 SQL、直写库存 |
| Controller | 鉴权依赖、DTO、调服务 | 改 `stock_balance` |
| Service | 状态机、仓库范围、幂等 | 绕过 `inventory_service` 改库存 |
| `inventory_service` | 行锁、数量、流水、审计 | 被助手或报表直接调用写路径以外的入口 |
| Agent | 查询 + 草稿 JSON | `execute_sql`、确认入库、完成出库 |

兼容壳：`backend/app/api/v1/*.py`、`frontend/src/api/*.ts` 只做再导出，新逻辑写 `controllers` / `models`。

## 3. 数据模型

### 3.1 ER 概览

```text
user_account ──┬── user_role ── role
               └── user_warehouse_scope ── warehouse ── warehouse_location
                                                      │
product ──────────────────────────────────────────────┤
                                                      │
                    stock_balance (product × location)┤  quantity / reserved / frozen
                    stock_ledger                      │
                    inbound_order ── inbound_item     │
                    outbound_order ── outbound_item ── picking_task
                    stock_count_order ── stock_count_item
                    transfer_order ── transfer_item
                    approval_task (business_type + business_id 唯一)
                    alert_ack (balance_id 唯一)
                    agent_session ── agent_message
                    audit_log
                    idempotency_record (user_id + key 唯一)
                    inbound_record / outbound_record   ← 历史只读，不回放
```

### 3.2 库存三字段

| 字段 | 含义 |
|---|---|
| `quantity` | 库位实物数量 |
| `reserved_quantity` | 已分配未完成出库 |
| `frozen_quantity` | 盘点待审批冻结 |

```text
available = max(0, quantity - reserved_quantity - frozen_quantity)
```

唯一约束：`(product_id, location_id)`。

盘点进入 `pending_approval` 时，对该行执行：

```text
frozen_quantity = max(0, quantity - reserved_quantity)
```

审批结束（过账或驳回）后清零冻结。出库分配只吃 `available`，不会动冻结部分。

### 3.3 流水 `stock_ledger`

| `transaction_type` | `quantity_delta` | 触发 |
|---|---|---|
| `inbound` | +n | 入库确认 |
| `outbound` | −n | 出库完成 |
| `count_gain` / `count_loss` | ±n | 盘点过账 |
| `transfer_out` / `transfer_in` | −n / +n | 调拨执行 |

`idempotency_key` 列全局唯一，格式 `{请求键}:{product_id}:{location_id}`。分配预留**不写流水**，只改 `reserved_quantity` 并记审计。

### 3.4 单据状态

| 实体 | 状态 |
|---|---|
| 入库单 | `draft` → `confirmed` |
| 出库单 | `draft` → `allocated` → `picked` → `reviewed` → `completed` |
| 拣货任务 | `allocated` → `picked`（整单完成后可视为 completed） |
| 盘点单 | `draft` / `counting` → `completed`（无差异）或 `pending_approval` → `applied` / `rejected` |
| 调拨单 | `draft` → 同仓可执行；跨仓 `pending_approval` 同意后再执行 |
| 审批任务 | `pending` → `approved` / `rejected` |
| 商品/库位 | `is_active`；停用后不可用于新作业 |

出库分配按 `location_id` 升序吃可用量，生成 `PK-{order_id}-{item_id}-{location_id}`。全部任务 `picked` 后单据升为 `picked`；复核后才能 `complete` 并 `deduct_reserved`。

跨仓判定：任一行源库位与目标库位的 `warehouse_id` 不同。创建人不能审批自己的盘点差异或跨仓调拨。

### 3.5 SKU

业务键：`source_product_code + brand`。系统 SKU：`MS-{source_product_code}-{brand}`。  
`product.pallet_capacity` 是托盘容量，**不是**库存。CSV 导入只写商品主数据。

历史表 `inbound_record` / `outbound_record` 来自 Mega Star 数据集，查询可以读，库存过账**禁止**回放。

## 4. 请求生命周期

```text
请求进入
  → 生成/透传 X-Request-ID
  → CORS
  → HTTPBearer 解析 JWT（HS256）
      jti 命中 erp:jwt:deny:{jti} → 401
      用户不存在或 is_active=0 → 401
  → require_roles ∩ 当前角色；空集 403
  → 非 admin：user_warehouse_scope；未绑定 403 WAREHOUSE_SCOPE_FORBIDDEN
  → Service：幂等命中则原样返回（replayed）
  → 库存写：缓存锁 + SELECT … FOR UPDATE
  → commit：单据 + balance + ledger + audit + idempotency_record
  → invalidate_stock_cache
失败：事务回滚；AppError → 统一 JSON + 运行日志 WARNING；未捕获 → INTERNAL_ERROR + ERROR 日志
```

### 4.1 错误信封

```json
{
  "code": "INVENTORY_INSUFFICIENT",
  "message": "库存不足",
  "request_id": "…",
  "details": { "product_id": 1, "required": 10, "shortage": 2 }
}
```

响应头带回 `X-Request-ID`。常见 `code`：

| code | HTTP | 场景 |
|---|---|---|
| `UNAUTHORIZED` | 401 | 无令牌、过期、已注销、账号停用 |
| `FORBIDDEN` | 403 | 角色不够 |
| `WAREHOUSE_SCOPE_FORBIDDEN` | 403 | 仓库范围不够 |
| `VALIDATION_ERROR` | 422 | Pydantic 校验 |
| `IDEMPOTENCY_KEY_REQUIRED` | 400 | 写操作缺头 |
| `INVENTORY_INSUFFICIENT` | 409 | 可用量不够分配 |
| `INVENTORY_STATE_INVALID` | 409 | 预留与实物不一致 |
| `ORDER_STATE_INVALID` / `TASK_STATE_INVALID` | 409 | 状态机拒绝 |
| `PRODUCT_INACTIVE` / `LOCATION_INACTIVE` | 409 | 主数据已停用 |
| `USERNAME_EXISTS` / `SKU_EXISTS` / `ORDER_NO_EXISTS` | 409 | 唯一键 |
| `USER_SELF_DELETE` / `LAST_ADMIN` | 409 | 账号保护 |
| `NOT_FOUND` | 404 | 资源不存在 |
| `INTERNAL_ERROR` | 500 | 未捕获异常；详情只在运行日志，响应不带堆栈 |

前端 `ApiError` 解析同一信封；网络失败 `code=NETWORK_ERROR`、`status=0`。

### 4.2 幂等

1. 读请求头 `Idempotency-Key`，空则 400。  
2. 查 `idempotency_record`：`(user_id, key)` 命中则返回第一次的 `response_body` / `status`。  
3. 业务成功后写入该表。  
4. 前端 `createIdempotencyKey('op')`：优先 `crypto.randomUUID()`。

同一用户重复提交同一键**不会**二次加库存或二次预留。不同用户的相同键互不影响。

### 4.3 运行日志

实现：`backend/app/core/logging.py`。`create_app()` 调用 `configure_logging()`。

- 每条 `LogRecord` 带 `request_id`（`contextvars`，与 `X-Request-ID` 相同）。
- 本机：stdout + `TimedRotatingFileHandler`（`backend/logs/app.log`，按天、保留 14 天）。
- pytest / Compose：默认不写文件，只看控制台或 `caplog`。
- 访问日志在中间件：方法、路径、状态、耗时；探活与 OpenAPI 为 DEBUG。
- `write_audit(..., request_id="api")` 会改用当前请求 ID。

Logger：`erp.http`、`erp.auth`、`erp.inventory`、`erp.agent`、`erp.cache`、`erp.runtime`。扩展新模块时用 `get_logger("模块名")`，不要把密钥打进消息。

更完整的查看方式和禁写清单见 [`docs/开发文档.md`](./开发文档.md) 第 12 节。

## 5. 并发控制

库存行同时使用两层锁：

1. **缓存互斥**：`erp:stock:lock:{product_id}:{location_id}`，`SET NX`，TTL 15s，最多重试 20×10ms。  
2. **MySQL 行锁**：`SELECT … FOR UPDATE` 落在同一事务。

`reserve()` 按商品加 `location_id=0` 的聚合锁，再锁所有有可用量的库位行，按 `location_id` 升序分配。SQLite 单测只验证业务逻辑，**不能**证明 InnoDB 行锁；压测必须用独立 `TEST_DATABASE_URL`，禁止指向 `erp_wms`。

## 6. 鉴权实现

### 6.1 密码

```text
pbkdf2_sha256$310000${salt_hex}${digest_hex}
```

16 字节随机盐；校验用 `hmac.compare_digest`。

### 6.2 JWT

HS256。载荷：`sub`（user_id）、`username`、`roles`、`jti`（uuid4 hex）、`iat`、`exp`。默认 60 分钟。生产 `SECRET_KEY` ≥ 32 位随机串。

注销：`erp:jwt:deny:{jti}` 写入缓存，TTL = 剩余有效期。无 Redis 时黑名单只在**当前进程**有效，多 worker 必须配 Redis。

### 6.3 角色别名

库内同时存在 `warehouse_operator` 与 `operator`。前端 `normalizedRoles` 把 `operator` 映射为 `warehouse_operator`。`admin` 的仓库范围为 `None`（全仓）；其他人必须绑定 `user_warehouse_scope`。删除用户为软停用，不能删自己或最后一个管理员。

前端守卫与菜单是体验层；后端 `require_roles()` 与 `ensure_warehouse_scope()` 是最终闸门。

## 7. 核心作业时序

### 7.1 入库确认

```text
POST /inbounds/{id}/confirm  + Idempotency-Key
  → 状态必须 draft
  → 商品/库位 is_active
  → apply_inbound：quantity += n，ledger inbound
  → 单据 confirmed，审计 inbound_confirm
```

收货页 `POST /receivings/{id}/confirm` 可按实收数量过账，同一套加库存路径。

### 7.2 出库闭环

```text
allocate  → reserve（无流水）→ 生成 picking_task → 单据 allocated
confirm   → 任务 picked；全部 picked → 单据 picked
review    → reviewed_by / reviewed_at / review_comment
complete  → deduct_reserved：quantity↓ reserved↓，ledger outbound
```

任一步失败整单回滚。库存不足：`409 INVENTORY_INSUFFICIENT`。

### 7.3 盘点

```text
保存实盘 → variance = counted - book
提交：全部 variance=0 → completed
      存在差异 → pending_approval + 冻结 + approval_task
同意 → apply_count_adjustment + 解冻
驳回 → 解冻，必填意见
```

### 7.4 调拨

```text
提交：同仓可直接待执行；跨仓进审批
执行：源库位 transfer_out，目标库位 transfer_in（可 create 目标余额行）
源 ≠ 目标；数量 > 0
```

## 8. 报表与预警算法

### 8.1 ABC

1. 分数：存在出库流水则用 `sum(-quantity_delta)`（`transaction_type=outbound`）；否则用现存量。  
2. `score == 0` 的 SKU **不入表**。  
3. 按分数降序、`product_id` 升序。  
4. 累计份额：`previous < 0.80` → A；`< 0.95` → B；其余 C。分类看**加入本行之前**的累计，不是加入之后。  
5. 可选 `days` 只限制出库窗口。

### 8.2 其它

| 报表 | 公式 / 规则 |
|---|---|
| 周转 | 出库量 / `max(现存, 1)` |
| 日报 / 周报 | 只统计 `stock_ledger`；`days` 1–31，`weeks` 1–12 |
| 拣货效率 | 完成率；确认耗时统一到 UTC，`max(0, Δt)` |

### 8.3 预警

默认阈值 `LOW_STOCK_THRESHOLD = 10`。

- `low_stock`：`available <= threshold`  
- `stale_stock`：可用高于阈值，且该商品在 `stock_ledger` 中**从未**出现 `outbound`（最多 50 条）

确认写入 `alert_ack`（按 `balance_id` 唯一）。补货草稿数量：`max(1, threshold - available)`。

看板 `erp:dashboard:summary` / `erp:dashboard:charts` TTL 30 秒；库存变更调用 `invalidate_stock_cache()`。

## 9. 智能助手

```text
用户消息（校验 session.user_id == 当前用户，history 只取该 session_id）
  → 最近 8 条**本会话**作为 history（不跨用户、不跨会话）
  → supervisor：问候直接说明能力；否则 DeepSeek plan_turn（失败则关键词）
        草稿（入/出库/盘点 +「草稿」，或 plan.draft_type）
        审批
        预警/异常
        ABC/周转/报表/看板/日报/周报/拣货效率
        默认库存（SKU 可来自本句、plan 或本会话上一句用户消息）
  → 对应 agent 节点调用 classify_and_run(history, plan)
  → assert_whitelist
  → polish_answer（可带本会话 history；保留「建议：」）
  → 多行结果自动 Markdown 表；用户说「制成表格」走 format_table
  → 低库存/预警/待办附下一步建议，不改库存
```

图是进程内单例，**没有** LangGraph checkpointer；每次 `invoke` 只带入当前会话 history。运行日志带 `user_id` 与 `session_id`，例如：

```text
erp.agent: session created user_id=1 session_id=12
erp.agent: message user_id=1 session_id=12 history_len=2
erp.agent: user_id=1 session_id=12 run history_len=2
erp.agent: user_id=1 session_id=12 intent=inventory source=keyword
erp.agent: session denied user_id=2 session_id=12 exists=True owner=1
```

不记录问题原文。列表接口只返回 `AgentSession.user_id = 当前用户` 的会话。

意图集合：`inventory` / `analysis` / `exception` / `draft` / `review`（规划器还可返回 `help`，按库存节点走说明文案）。  
SKU 正则：`SKU-…` 或 `MS-…`；匹配 `sku_code` / `source_product_code` / `product_name`。同一会话未提 SKU 时，优先沿用最近一条用户消息里的编码。

白名单含查询、制表、三种草稿、`submit_for_approval`。禁止：`execute_raw_sql`、`update_stock_balance`、无人确认的入出库。草稿必须到业务页人工保存；助手不得声称已经改库存。

LLM：`DEEPSEEK_API_KEY` 空则纯关键词 + 会话 SKU 沿用；有 Key 时 `plan_turn` 规划槽位，超时约 12s，temperature 0.2。会话表 `agent_session` / `agent_message`（JSON 存 `tool_calls`、`draft`）。

## 10. 前端运行时

```text
LoginView → Pinia login → localStorage[smart-erp-wms-access-token]
```

## 12. 迁移与安全边界

Alembic 只增不删：`0001` 账号作业核、`0002` 盘点调拨审批、`0003` 助手/预警/复核、`0004` `is_active`/`frozen_quantity`、`0005` `alert_ack.updated_at`。

对 `erp_wms` 必须 `--allow-erp-wms`。`downgrade()` 禁用。禁止再跑带 `DROP TABLE` 的 `database/schema.sql`。

测试：后端默认 SQLite 内存（`backend/tests`）；前端 Vitest。密钥、管理员密码、数据库口令不进仓库；密码文件仅本机 `backend/.admin-password`。
